## 1. Выбрать прибор → забронировать → вернуться к списку

В `navigation/routes.js` объявлены три разрыва сценария:

| Замечание и основание | Необходимое изменение |
|---|---|
| Пункт «Приборы» ведёт на `/help/equipment`, где только правила и нет дальнейших ссылок. Каталог находится на `/catalog`. | Направить пункт на `/catalog`. Правила оставить отдельной вспомогательной ссылкой. |
| `catalogLink` сохраняет текущий URL в `returnTo`, но у `/items/:id` задан постоянный `back: '/catalog'`. В этой конфигурации нет использования переданного контекста. | Возвращать к поддерживаемому URL списка из `returnTo`, включая `search` и `page`; при прямом входе в карточку использовать `/catalog`. Восстанавливать позицию списка и фокус выбранной строки. |
| `historyLink` открывает `/history/items/:id` без действий, хотя комментарий прямо задаёт одинаковые права оператора из каталога и истории. | Использовать одну карточку прибора по стабильному `id` с действием бронирования, передавая контекст возврата из обоих списков. Старый маршрут истории можно сохранить как совместимый вход в эту карточку. Источник перехода определяет возврат, а не права. |

После бронирования показать в карточке результат для конкретного `itemId`: `reserve` уже возвращает этот идентификатор и `status: 'reserved'`. Кнопка возврата должна оставаться доступной и сохранять контекст списка. При подключении реального запроса нужны состояние отправки, защита от повторного нажатия и ошибка с повтором; результат нельзя переносить на другой открытый прибор.

**Выполненная проверка:** модуль загружен и исполнен в Node. Семь утверждений подтвердили адрес пункта меню, отсутствие действий у карточки истории, результат `reserve` и путь карточки. Для `/catalog?search=Измеритель&page=3` ссылка корректно кодирует и восстанавливает полный `returnTo`, тогда как объявленный `back` остаётся `/catalog`. Это проверка функций и конфигурации, не маршрутизатора или браузерного возврата.

**Приёмка после реализации:** пройти сценарий из отфильтрованной третьей страницы, из истории и по прямой ссылке; проверить доступность бронирования, принадлежность результата прибору и восстановление исходного списка. Эти проверки пока не выполнены.

## 2. Страница «Расходники»

Продолжить складскую страницу из `new-screen/existing.html`: заголовок, подписанный поиск и плотная таблица. Отдельный выбор художественного направления не требуется: `new-screen/decisions.md` уже закрепляет нейтральный фон, синий акцент, радиус 6 px и плотные строки. Фиолетовые округлые карточки акции сюда не переносятся.

Предлагаемое устройство:

- **Поиск «Название или код расходника».** Фильтрует список; запрос сохраняется после заказа. При отсутствии совпадений показать «Ничего не найдено» и действие очистки поиска.
- **Строка: название и видимый код → остаток с единицей → текстовый статус → «Заказать».** Название не уникально, поэтому выбор, ключ строки, запрос и сообщение результата привязать к стабильному идентификатору. Длинные названия переносить, сохраняя код и действие читаемыми.
- **Остатки из общей модели склада.** Например, `6 шт.` / «В наличии», `0 шт.` / «Нет в наличии». Неизвестное значение не подменять нулём. Цвет всегда дополняет текст; допустимый нулевой остаток сам по себе не повод красить строку как ошибку.
- **Заказ доступен и при нуле.** Перед таблицей коротко пояснить: «Заказать — отправить заявку. При нулевом остатке создаётся заявка на пополнение». В строке с нулём повторить смысл действия: «Заявка на пополнение». Не обещать немедленную выдачу.
- **Результат у соответствующей строки.** Во время отправки блокировать её повторный заказ; затем показать «Заявка отправлена» или «Заявка на пополнение отправлена». При ошибке дать понятный повтор, сохранив поиск. Красный использовать для ошибки, требующей внимания.

**Выполненная проверка:** сопоставлены все решения с `new-screen/decisions.md` и структура/токены с `new-screen/existing.html`; изучен именно исходник HTML. Проектное решение сохраняет действующую систему и трактовку заказа. Макет, рендер и поведение новой страницы не создавались и не проверялись.

**Приёмка будущей страницы:** две позиции с одинаковыми названиями и разными ID, длинная кириллица, разные единицы, нулевой/неизвестный остаток, пустой результат поиска и ошибка отправки. Проверить заказ нужного ID, сохранение запроса, текст статуса и доступность действия с клавиатуры. Это план проверки, не результаты испытаний.

## 3. Замена общего компонента кнопки

Сравнены `shared/base/Button.jsx` и `shared/current/Button.jsx`, прочитаны все три предоставленных места использования.

| Вывод | Последствие и исправление |
|---|---|
| **Регрессия: удалён `disabled`.** `shared/current/Reservation.jsx` передаёт `disabled={pending}`. | Новая кнопка игнорирует блокировку и допускает повторные вызовы обработчика во время отправки. Вернуть параметр с прежним значением по умолчанию и передачу в нативный `<button>`. Сам факт повторных серверных бронирований по этим файлам не доказан. |
| **Регрессия: удалён `type`.** В `shared/current/FilterForm.jsx` заданы разные типы для «Сбросить» и «Применить». | Кнопка без типа внутри формы становится submit: нажатие «Сбросить» способно вызвать `reset`, а затем `apply`, если обработчик не отменяет отправку. Вернуть `type = 'button'` и передачу явного типа. «Применить» пока остаётся submit по умолчанию браузера, но это не сохранение контракта компонента. |

| **Непроверенное визуальное изменение:** `action--compact` теперь добавляется всем кнопкам. | Правила этого класса не предоставлены. Нельзя утверждать, что размер, контраст или зона нажатия ухудшились. Проверить фактический стиль во всех трёх местах; если компактность нужна только отдельным случаям, сделать её явным вариантом. |

**Выполненная проверка:** текстовый diff подтвердил удаление двух параметров и добавление класса; статически прослежены последствия во всех предоставленных потребителях. JSX не рендерился, CSS класса и реализаций обработчиков нет.

**Приёмка исправления:** при `pending=true` бронирование не вызывается нажатием; «Сбросить» вызывает только сброс, «Применить» — отправку формы; у справки есть доступное имя. Отдельно проверить фокус, активацию клавиатурой и фактический размер кнопок. Эти проверки ещё предстоят.

Локальный вывод для этого набора: сохранить контекст списка, действующий контракт общего компонента и принятый складской стиль. Предложения основаны на исходниках; они не подтверждают пользовательское предпочтение или качество ещё не показанного интерфейса.
