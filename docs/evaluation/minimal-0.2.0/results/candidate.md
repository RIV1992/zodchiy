# Ревью интерфейса проката

Основание — предоставленные исходники. Ни работающий интерфейс, ни пользовательские испытания не наблюдались. В заданиях 1–3 ниже предложены изменения; код не менялся.

## 1. Выбор прибора, бронирование и возврат

В `navigation/routes.js` нарушены три части пути:

- **Обычный вход.** Пункт «Приборы» ведёт на `/help/equipment`, где нет дальнейших ссылок. У главной страницы есть только переход в историю. Направить «Приборы» на `/catalog`; справку оставить отдельным вспомогательным входом.
- **Один прибор из разных списков.** Каталог открывает `detail` с `reserve`, история — `summary` без действий. Права оператора одинаковы, `id` и название берутся из общего хранилища: оснований для запрета бронирования из истории нет. Использовать одну карточку `/items/:id` с бронированием для обоих входов. Исторические сведения при необходимости показывать в ней как контекст. Старую ссылку `/history/items/:id` направлять в ту же карточку с возвратом в историю.
- **Возврат с контекстом.** `catalogLink` передаёт текущий URL в `returnTo`, но `back` всегда равен `/catalog`: поиск и страница теряются. Использовать проверенный локальный `returnTo` для разрешённых списков, включая `search` и `page`; передавать исходный URL и из истории. Для прямого входа или недопустимого значения — `/catalog`. После бронирования показывать результат для `itemId`, полученного от `reserve`, и сохранять тот же адрес возврата. Ответ по прибору A не должен становиться сообщением об успехе для B при смене карточки.

**Выполненная проверка:** модуль исполнен в Node.js. Обход объявленных обычных входов и статических `links` не достигает каталога; ссылка для прибора `equipment-17` сохраняет в `returnTo` кириллический поиск и `page=3`, а объявленный `back` их отбрасывает. Проверены разные наборы действий и возврат `{itemId, status: 'reserved'}`. Это проверка модели маршрутов, не браузерный проход.

**После исправления:** пройти из меню поиск → страницу 3 → карточку → бронирование → тот же список; повторить из истории для того же `id`, проверить прямой вход и смену A на B до завершения запроса.

## 2. Страница «Расходники»

Предлагается продолжить устройство `new-screen/existing.html`: заголовок, подписанный поиск, плотная таблица «Название / Код / Остаток / Статус / Действие». Код — стабильный идентификатор позиции: одинаковые названия должны различаться и визуально, и в заявке. Поиск — по названию и коду; остаток — количество с единицей из общей складской модели.

В строке — действие «Заказать». Оно открывает компактную форму для выбранной позиции: название и код, количество с единицей, отправка заявки. Краткая подпись объясняет, что заказ означает заявку, а не немедленную выдачу. При нуле показывать «0 [единица]», «Нет в наличии» и пояснение о заявке на пополнение; заказ остаётся доступным. Не ограничивать количество текущим остатком без отдельного продуктового основания. Результат отправки привязывать к идентификатору позиции; после закрытия сохранять поиск и место в списке.

Из `new-screen/decisions.md` наследуются нейтральный фон, синий акцент, радиус 6 px, плотные строки и текст рядом со статусом. Фиолетовые крупные карточки с радиусом 24 px относятся только к акции «День мастерской». Нулевой остаток сам по себе не требует красного: это допустимое состояние. Красный уместен для ошибки отправки или загрузки. При неизвестном остатке писать «Нет данных», не подставлять ноль; отдельно предусмотреть загрузку и пустую выдачу поиска.

**Выполненная проверка:** предложение сверено с обоими файлами `new-screen/`: сохранены общая модель, смысл «Заказать» и область рекламного исключения. Это проектное решение, без реализации и визуальной приёмки. После реализации достаточно проверить одинаковые названия с разными кодами, длинную кириллицу, нулевой и неизвестный остаток, ошибку заявки и возврат к поиску; эти проверки ещё не выполнены.

## 3. Замена общей кнопки

Сопоставлены `shared/base/Button.jsx`, `shared/current/Button.jsx` и все три предоставленных потребителя.

| Место | Последствие и происхождение | Необходимое исправление |
|---|---|---|
| `shared/current/Reservation.jsx` | Новая регрессия: `disabled={pending}` больше не доходит до DOM. Во время ожидания кнопка остаётся активной и позволяет снова вызвать `createReservation`. | Вернуть приём и передачу `disabled`, сохранив значение по умолчанию `false`. |
| `shared/current/FilterForm.jsx` | Новая регрессия: `type="button"` игнорируется. В форме «Сбросить» становится submit-кнопкой: после `reset` может запускать отправку и `apply`. «Применить» остаётся submit по умолчанию, поэтому само по себе не сломано. | Вернуть `type` с исходным значением по умолчанию `'button'` и передачей явного `'submit'`. |
| `shared/current/Settings.jsx` | Прежний дефект обеих версий: содержимое — только `svg` с `aria-hidden="true"`; доступного имени нет. | Добавить имя «Открыть справку» и поддержку передачи `aria-label` в DOM в `Button`. Одного атрибута в месте вызова недостаточно. |

`action--compact` — новое визуальное изменение, но его CSS в материалах отсутствует. Уменьшение области нажатия, обрезание текста и ухудшение фокуса не доказаны. Перед принятием этого класса сравнить обе версии с реальными стилями в трёх перечисленных местах, включая длинную подпись и узкий контейнер.

**Выполненная проверка:** просмотрен diff кнопки; поиском найдены и прочитаны все четыре использования `Button` в трёх предоставленных экранах. Выводы о потерянных свойствах и прежнем отсутствии имени основаны на коде. После исправления проверить: при `pending` нет повторного вызова; «Сбросить» вызывает только `reset`; «Применить» и отправка формы с клавиатуры вызывают `apply`; кнопка справки имеет имя и доступна с клавиатуры. React и браузер не запускались, графические последствия не проверены.
